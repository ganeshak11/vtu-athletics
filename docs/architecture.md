# 1. Entity Model: Squads, Not Colleges-With-Login-Codes

The old design put `boys_login_code` and `girls_login_code` on a `colleges` table.
The real entity is a **squad**: a college fielding a team for a specific gender division.
Credentials, payment status, roster locks, and bid block ranges all attach to the squad.

```
colleges
  id              UUID PK
  name            TEXT NOT NULL         -- "MIT Mysore"
  code            TEXT UNIQUE NOT NULL  -- "MITM"
  district        TEXT
  created_at      TIMESTAMPTZ

squads
  id              UUID PK
  college_id      UUID FK → colleges
  gender          TEXT CHECK (gender IN ('men', 'women'))
  passphrase_hash TEXT NOT NULL         -- bcrypt/argon2 hash
  ped_name        TEXT NOT NULL
  ped_phone       TEXT NOT NULL
  ped_email       TEXT
  roster_locked   BOOLEAN DEFAULT FALSE
  payment_status  TEXT DEFAULT 'DRAFT'
    CHECK (payment_status IN ('DRAFT','SUBMITTED','VERIFIED','REJECTED'))
  bid_block_start INT                   -- set on registration close
  bid_block_end   INT                   -- set on registration close
  created_at      TIMESTAMPTZ

  UNIQUE (college_id, gender)           -- one squad per college per gender
```

### Authentication for Squads

The login credential is: **squad code + passphrase**.

- Squad code: derived as `<COLLEGE_CODE>-M` or `<COLLEGE_CODE>-G` (deterministic, not secret).
- Passphrase: a random 6-word phrase or 8-char alphanumeric string, generated by the system and shared privately with the PED coordinator. Stored as a bcrypt hash. **Not guessable from the college name.**

Login flow:
```
Enter Squad Code:    MITM-M
Enter Passphrase:    ●●●●●●●●
                        │
                        ▼
        bcrypt.compare(input, squads.passphrase_hash)
                        │
              ┌─────────┴──────────┐
              ▼                    ▼
           Match                No Match
              │                    │
              ▼                    ▼
     Create session             Reject
     (role: 'squad_manager',
      squad_id: ...)
```

Alternative: OTP to PED's registered phone. Depends on whether SMS infra is available.
For MVP, passphrase is sufficient. OTP can be layered on later.

# 2. Staff Roles & Permission Matrix

## 2.1 Role Definitions

| Role | Who | How They Authenticate | What They Access |
| :--- | :--- | :--- | :--- |
| `squad_manager` | Principal / PED | Squad code + passphrase | Own squad roster, payment submission, athlete cards |
| `meet_admin` | Meet Director, Technical Director | Username + password (pre-provisioned) | Everything. Registration lock, bid generation, event config, scoring rules, payment verification |
| `finance_desk` | Host college finance staff | Username + password | Payment verification desk only. Cannot modify rosters or results |
| `accreditation_volunteer` | Campus volunteers at entry gate | PIN assigned by admin (4–6 digit) | Scan QR → mark athlete ACCREDITED. Read-only on athlete data |
| `warden` | Hostel staff | PIN assigned by admin | Scan QR → mark accommodation check-in. Read-only otherwise |
| `call_room_official` | Track marshals, call room staff | PIN assigned by admin | Scan QR → update call room status. View heat rosters. Reserve substitution |
| `referee` | Chief referee, event judges | PIN assigned by admin, scoped to event(s) | Enter results (track times, field attempts). Cannot modify rosters or payments |
| `spectator` | Public | No auth required | Read-only: `/live` results, `/leaderboard` standings |

## 2.2 Staff Table

```
staff
  id              UUID PK
  username        TEXT UNIQUE           -- NULL for PIN-based roles
  pin             TEXT                   -- hashed, NULL for username-based roles
  password_hash   TEXT                   -- NULL for PIN-based roles
  display_name    TEXT NOT NULL
  role            TEXT NOT NULL
    CHECK (role IN ('meet_admin','finance_desk','accreditation_volunteer',
                    'warden','call_room_official','referee'))
  scope_event_ids UUID[]                -- referees: which events they judge
  is_active       BOOLEAN DEFAULT TRUE
  created_at      TIMESTAMPTZ
```

## 2.4 Session Model

All sessions use encrypted HTTP-only cookies (iron-session or equivalent).
Session payload:

```typescript
{
  role: 'squad_manager' | 'meet_admin' | 'finance_desk' | ... | 'spectator';
  entity_id: string;       // squad.id for squad_manager, staff.id for staff roles
  college_id?: string;     // set for squad_manager
  squad_id?: string;       // set for squad_manager
  gender?: 'men' | 'women'; // set for squad_manager
  scope_event_ids?: string[]; // set for referee
}
```

Every server action begins with `requireRole(...)` which validates the session
and extracts the scoped entity.

# 3. Corrected Data Model

## 3.1 Registrations: Normalized Junction Table

**Old (wrong)**:
```
profiles.event1_id, profiles.event2_id, profiles.reserve_event_id,
profiles.is_relay, profiles.is_half_marathon
```

**New (correct)**:
```
profiles
  id                UUID PK
  squad_id          UUID FK → squads NOT NULL
  sslc_name         TEXT NOT NULL
  usn               TEXT NOT NULL
  semester          INT CHECK (semester BETWEEN 1 AND 8)
  blood_group       TEXT NOT NULL
  college_joining_date  DATE NOT NULL
  sem_start_date    DATE NOT NULL
  bid_number        INT                 -- assigned on registration close
  accreditation_status TEXT DEFAULT 'REGISTERED'
    CHECK (accreditation_status IN ('REGISTERED','ACCREDITED'))
  accredited_at     TIMESTAMPTZ
  accommodation_checked_in BOOLEAN DEFAULT FALSE
  accommodation_checked_in_at TIMESTAMPTZ
  created_at        TIMESTAMPTZ

registrations
  id                UUID PK
  profile_id        UUID FK → profiles NOT NULL
  event_id          UUID FK → events NOT NULL
  kind              TEXT NOT NULL
    CHECK (kind IN ('regular','reserve','relay','half_marathon'))
  created_at        TIMESTAMPTZ

  UNIQUE (profile_id, event_id)         -- no duplicate event entries
```

**Quota constraints (enforced by triggers or application logic, documented here):**
- `COUNT(*) WHERE kind = 'regular' AND profile_id = X` ≤ 2
- `COUNT(*) WHERE kind = 'reserve' AND profile_id = X` ≤ 1
- A reserve event must differ from all regular events for the same athlete.
- `COUNT(*) WHERE kind = 'relay' AND squad_id = S` ≤ 4 (per squad, i.e. per college per gender)
- No limit on `half_marathon` count per squad.

**Fee computation becomes a query:**
```sql
SELECT SUM(
  CASE kind
    WHEN 'regular' THEN 100
    WHEN 'relay' THEN 100
    WHEN 'half_marathon' THEN 100
    WHEN 'reserve' THEN 0
  END
) AS total_fee
FROM registrations r
JOIN profiles p ON r.profile_id = p.id
WHERE p.squad_id = :squad_id;
```

## 3.2 Payments: Multiple Submissions, Rejection, Amount Matching

```
payments
  id                UUID PK
  squad_id          UUID FK → squads NOT NULL
  amount_submitted  INT NOT NULL        -- what the PED claims to have paid
  amount_expected   INT                 -- computed by system at submission time
  utr_number        TEXT NOT NULL
  screenshot_url    TEXT NOT NULL        -- Supabase Storage path
  status            TEXT DEFAULT 'SUBMITTED'
    CHECK (status IN ('SUBMITTED','VERIFIED','REJECTED'))
  rejection_reason  TEXT                -- required when status = 'REJECTED'
  verified_by       UUID FK → staff     -- who approved/rejected
  verified_at       TIMESTAMPTZ
  created_at        TIMESTAMPTZ

  UNIQUE (utr_number)                   -- prevent same UTR used by two squads
```

**Rules:**
- A squad can submit multiple payment rows (e.g., partial payment, top-up after adding athletes).
- `squad.payment_status` is derived: `VERIFIED` only when `SUM(amount_submitted) WHERE status = 'VERIFIED'` ≥ computed fee.
- Roster edits are locked on first payment submission (`squad.roster_locked = TRUE`).
  To add athletes after payment, the PED must request admin unlock → admin reopens roster → PED adds athletes → system recalculates fee → PED submits a top-up payment.
- Rejected payments can be resubmitted with a corrected UTR.

## 3.3 Relay Teams: Proper Entity

Relays are team events. Results are per-team, not per-athlete.

```
relay_teams
  id                UUID PK
  squad_id          UUID FK → squads NOT NULL
  event_id          UUID FK → events NOT NULL    -- e.g., "4x100m Men"
  created_at        TIMESTAMPTZ

  UNIQUE (squad_id, event_id)           -- one relay team per squad per relay event

relay_members
  id                UUID PK
  relay_team_id     UUID FK → relay_teams NOT NULL
  profile_id        UUID FK → profiles NOT NULL
  leg_order         INT CHECK (leg_order BETWEEN 1 AND 4)
  is_reserve        BOOLEAN DEFAULT FALSE
  created_at        TIMESTAMPTZ

  UNIQUE (relay_team_id, leg_order)     -- one athlete per leg
  UNIQUE (relay_team_id, profile_id)    -- athlete cannot run twice on same relay
```

**Rules:**
- A relay team has exactly 4 running members + up to 2 reserves (configurable).
- Athletes on a relay team do NOT consume a "regular event" slot.
  Relay registration is separate from individual event registration.
- Relay results attach to `relay_team_id`, not `profile_id`.
- Points earned by a relay go to the **college**, not to individual athletes.
  Therefore relay points don't count toward "Best Athlete" trophies.

**Relay events in scope for this meet:**
- 4x100m (Men & Women)
- 4x400m (Men & Women)

Both are in scope. The old plan listed only 4x100m in registration but 4x400m in results.
Both must be registered and scored.

## 3.4 Events: Category-Aware Configuration

```
events
  id                UUID PK
  name              TEXT NOT NULL        -- "100m", "Shot Put", "High Jump"
  code              TEXT UNIQUE NOT NULL -- "100M", "SP", "HJ"
  gender            TEXT CHECK (gender IN ('men','women','mixed'))
  category          TEXT NOT NULL
    CHECK (category IN ('track_sprint','track_distance','track_hurdles',
                        'field_throw','field_horizontal_jump',
                        'field_vertical_jump','relay','road','combined'))
  measurement_unit  TEXT
    CHECK (measurement_unit IN ('seconds','metres','points',NULL))
  start_type        TEXT NOT NULL
    CHECK (start_type IN ('lanes','waterfall','mass','road'))
  max_lanes         INT                 -- NULL for mass/waterfall/road starts
  has_rounds        BOOLEAN DEFAULT FALSE  -- TRUE = heats → semis → final
  is_multi_attempt  BOOLEAN DEFAULT FALSE  -- TRUE for throws, jumps
  is_progressive_height BOOLEAN DEFAULT FALSE  -- TRUE for HJ, PV only
  max_attempts_per_height INT           -- 3 for HJ/PV, NULL otherwise
  created_at        TIMESTAMPTZ
```

**Start types by event:**

| Event | `start_type` | `max_lanes` | `has_rounds` |
| :--- | :--- | :---: | :---: |
| 100m, 200m, 400m | `lanes` | 8 | TRUE (heats → final) |
| 110m/400m Hurdles | `lanes` | 8 | TRUE |
| 800m | `waterfall` | NULL | TRUE (heats → final) |
| 1500m, 5000m, 10000m | `mass` | NULL | FALSE (timed final) |
| 4x100m, 4x400m Relay | `lanes` | 8 | FALSE (single final) |
| 21km Half Marathon | `road` | NULL | FALSE |
| Shot Put, Discus, Javelin | `mass` (field) | NULL | FALSE |
| Long Jump, Triple Jump | `mass` (field) | NULL | FALSE |
| High Jump, Pole Vault | `mass` (field) | NULL | FALSE |

**Round advancement logic (when `has_rounds = TRUE`):**
- Configurable per event: top N per heat auto-qualify (`Q`), next M fastest qualify (`q`).
- Stored in a `qualification_rules` JSONB column or separate table.
- For MVP, we support: heats → final only (no semi-finals).

## 3.5 Results: Split Track vs. Field vs. Progressive Height

```
event_results
  id                UUID PK
  event_id          UUID FK → events NOT NULL
  round_id          UUID FK → event_rounds NOT NULL
  heat_id           UUID FK → event_heats    -- NULL for field/mass events
  profile_id        UUID FK → profiles       -- NULL for relay events
  relay_team_id     UUID FK → relay_teams    -- NULL for individual events
  lane_number       INT                      -- NULL for non-lane events
  status            TEXT DEFAULT 'SEEDED'
    CHECK (status IN ('SEEDED','REPORTED','DNS','DNF','DQ','FINISHED'))
  final_result      NUMERIC                  -- seconds for track, metres for field
  rank              INT
  qualified         BOOLEAN
  wind_reading      NUMERIC                  -- for sprints and horizontal jumps
  created_at        TIMESTAMPTZ

  -- Exactly one of profile_id or relay_team_id must be non-null
  CHECK (
    (profile_id IS NOT NULL AND relay_team_id IS NULL) OR
    (profile_id IS NULL AND relay_team_id IS NOT NULL)
  )

field_attempts
  id                UUID PK
  result_id         UUID FK → event_results NOT NULL
  attempt_number    INT NOT NULL CHECK (attempt_number BETWEEN 1 AND 6)
  distance          NUMERIC              -- metres, NULL if foul/pass
  outcome           TEXT NOT NULL
    CHECK (outcome IN ('valid','foul','pass','no_mark'))
  created_at        TIMESTAMPTZ

  UNIQUE (result_id, attempt_number)

progressive_height_attempts
  id                UUID PK
  result_id         UUID FK → event_results NOT NULL
  bar_height        NUMERIC NOT NULL     -- metres (e.g. 1.85, 1.90, 1.95)
  attempt_1         TEXT CHECK (attempt_1 IN ('O','X','-'))  -- O=clear, X=fail, -=pass
  attempt_2         TEXT CHECK (attempt_2 IN ('O','X','-',NULL))
  attempt_3         TEXT CHECK (attempt_3 IN ('O','X','-',NULL))
  cleared           BOOLEAN GENERATED ALWAYS AS
                      (attempt_1 = 'O' OR attempt_2 = 'O' OR attempt_3 = 'O') STORED
  created_at        TIMESTAMPTZ

  UNIQUE (result_id, bar_height)
```

**Ranking rules by category:**
- **Track** (`seconds`): ascending (lowest time wins). Ties broken by thousandths of a second.
- **Field throws & horizontal jumps**: descending `best_mark = MAX(valid attempts)`. Ties broken by second-best mark, then third-best.
- **High Jump / Pole Vault**: highest bar cleared, then fewest total failures at that height, then fewest total failures overall. (Standard IAAF countback.)
- **Relay**: same as track (ascending time). Points go to college, not individual athletes.
- **DNS/DNF/DQ**: no rank, no points awarded.

## 3.6 Scoring: Configurable & Explicit Edge Cases

```
scoring_config
  id                UUID PK
  rank              INT NOT NULL          -- 1, 2, 3, ...
  points            INT NOT NULL          -- 8, 7, 6, ...

  UNIQUE (rank)
```

Default configuration for this meet:

| Rank | Points |
| :---: | :---: |
| 1 | 8 |
| 2 | 7 |
| 3 | 6 |
| 4 | 5 |
| 5 | 4 |
| 6 | 3 |

**Explicit edge case rules:**
- **DNS/DNF/DQ**: 0 points. No rank awarded.
- **Ties in individual events**: Both athletes receive the higher rank's points. Next rank is skipped. (E.g., two athletes tie for 1st → both get 8 pts, no 2nd place, next athlete gets 3rd = 6 pts.)
- **Relay points**: Points go to the **college total** only. They do NOT count toward individual "Best Athlete" awards.
- **"Best Athlete" tie-breaker**: More golds wins. If still tied, more silvers wins. If still tied, more bronzes. If still tied, co-champions.
- **"Best College" tie-breaker**: More golds → more silvers → more bronzes → co-champions.
- **Half Marathon**: scored like any other event (top 6 get points).

# 4. Post-Close Amendment Flow

Registration close is not a one-way door. Real meets need post-close corrections.

```
   Normal Flow:
   Registration OPEN ──► Admin clicks "Close" ──► Bid numbers generated

   Amendment Flow:
   Registration CLOSED
        │
        ▼
   PED contacts Meet Director (phone/email)
        │
        ▼
   Admin opens /admin/amendments
        │
        ├── "Withdraw Athlete" ──► Athlete marked withdrawn, bid number voided
        │                          (Bid number gap is preserved, NOT reassigned)
        │
        ├── "Substitute Athlete" ──► New athlete takes withdrawn athlete's bid number
        │                            and event registrations
        │
        └── "Add Late Entry" ──► New athlete gets next available bid number
                                  at the END of their college's block
                                  (requires top-up payment if fee increases)
```

**Key rule:** Bid numbers are NEVER reassigned or renumbered after generation.
Gaps from withdrawals are permanent. This prevents confusion on printed heat sheets.

# 5. Accreditation Identity Verification

A QR code containing only an Athlete ID is trivially shareable (screenshot forwarding).

**Mitigation (practical for a college meet):**
- The accreditation desk volunteer is instructed to verify the athlete's physical **college student ID card** alongside the digital QR scan.
- The system displays the athlete's name, college, and photo (if captured) on the volunteer's screen after scanning, for visual cross-check.
- **MVP**: No biometric. Just QR scan + physical ID card check + visual name confirmation.
- **Future**: Add a passport-size photo upload during registration for on-screen display at accreditation.

# 6. Offline & Connectivity Strategy

Stadium and campus Wi-Fi is unreliable. The system must degrade gracefully.

**Design:**
- Scanner desks (accreditation, warden, call room, canteen) use **Service Worker caching** with a local IndexedDB write queue.
- Each scan generates a **client-side UUID** (idempotency key).
- When connectivity returns, queued scans are replayed to the server.
- Server enforces idempotency: if a scan with the same UUID already exists, it returns success without duplicating.
- **Conflict rule**: If an athlete is scanned offline on two devices simultaneously, the first write wins. The second returns "already processed" on sync.
- **Live results (`/live`)**: Served from a server-side cache with a 10-second TTL, not from Supabase Realtime WebSocket connections. Spectators poll; they don't hold persistent connections.
- **Admin desks**: Admin and referee interfaces use Supabase Realtime for immediate sync (low connection count, high-value updates).

# 7. Platform Decision: PWA vs. Capacitor

| Capability | PWA | Capacitor Native |
| :--- | :--- | :--- |
| QR Scanning | ✅ WebRTC camera API | ✅ Native camera plugin |
| Offline caching | ✅ Service Worker | ✅ Service Worker |
| Push notifications | ⚠️ Requires HTTPS + user opt-in, no iOS Safari support | ✅ FCM (Android) + APNs (iOS) |
| Installation friction | ✅ Zero. Share a link | ❌ Play Store review + sideload for iOS |
| Update speed | ✅ Instant (next page load) | ❌ Requires app store resubmission |

**Decision for MVP**: Ship as a **PWA**. Athletes won't install an app for a 4-day meet.
Share a link via WhatsApp. Notifications delivered via WhatsApp broadcast or SMS.

**Reassess Capacitor** only if:
- iOS push notifications become a hard requirement AND
- WhatsApp/SMS broadcast is insufficient for call room alerts.

# 9. Open Questions (Must Answer Before Stage 1)

| # | Question | Impact |
| :--- | :--- | :--- |
| 1 | **How many days until the meet?** | Determines whether all 14 modules are realistic or we cut to a critical-path slice. |
